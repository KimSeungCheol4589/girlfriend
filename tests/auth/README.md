# 인증 E2E와 픽스처 — 로컬 전용

이 디렉터리는 **로컬 Supabase 인스턴스에서만** 실행한다. 합성 계정(`*.test.invalid`)만 만들고
비밀번호는 실행할 때마다 새로 생성한다. 키·비밀번호·토큰은 출력하지 않는다.

```text
tests/auth/
  fixtures/   준비·정리 스크립트 (node로 직접 실행)
  e2e/        Playwright 스펙 (playwright.auth.config.ts)
  reporters/  실패 산출물에서 페이지 스냅샷을 지우는 리포터
```

## 1. 안전장치

- Supabase 주소가 loopback(`127.0.0.1` / `localhost` / `::1`)이 아니면 **즉시 중단**한다.
- `NODE_ENV=production`이면 실행하지 않는다.
- 계정 이메일 도메인은 `test.invalid`로 고정돼 있다. 다른 도메인의 계정은 만들지도 지우지도 않는다.
- 비밀번호는 `crypto.randomBytes`로 매번 새로 만들고 `.agent-runtime/auth-e2e/accounts.json`
  (Git 제외 경로, 파일 권한 0600)에만 저장한다. 화면·로그에 찍지 않는다.
- 픽스처는 컨테이너를 만들거나 지우거나 재시작하지 않는다. 이미 떠 있는 DB 컨테이너에서 `psql`만 쓴다.
- Playwright 설정은 trace·video·screenshot을 끈다. 그래도 실패하면 `error-context.md`가 생기고
  그 안의 aria 스냅샷에는 **입력 필드 값이 그대로** 담긴다(`type="password"` 필드 포함).
  설치된 1.63.0으로 직접 실험한 결과 `PLAYWRIGHT_NO_COPY_PROMPT=1`은 **효과가 없었다.**
  그래서 리포터(`tests/auth/reporters/redact-error-context.ts`)가 파일이 만들어진 뒤
  **스냅샷 블록만 덜어 낸다.** 오류 메시지·호출 로그·테스트 소스는 그대로 남는다.
- 단언에 비밀 값을 넣지 않는다. 비교가 필요하면 `expect(a === b).toBe(true)`처럼 boolean으로 바꾼다.
  토큰이 들어간 주소는 `pathnameOf(page)`로 경로만 단언한다.
- 앱 서버는 `127.0.0.1:3002`에만 바인딩한다(데모 E2E는 3001, 통합 앱은 3000).

## 2. 필요한 환경 변수

앱 변수와 이름을 분리했다. 아래 값은 **로컬 테스트 인스턴스의 것만** 넣는다.

| 이름 | 필수 | 설명 |
| --- | --- | --- |
| `AUTH_TEST_SUPABASE_URL` | 예(또는 `NEXT_PUBLIC_SUPABASE_URL`) | 로컬 API 주소. 예: `http://127.0.0.1:56321` |
| `AUTH_TEST_SERVICE_ROLE_KEY` | 예 | 합성 계정 생성·삭제와 복구 링크 생성용. 앱은 읽지 않는다 |
| `AUTH_TEST_ANON_KEY` | 예(또는 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`) | 앱 서버에 전달할 공개 키. 세션 폐기 호출에도 쓴다 |
| `AUTH_TEST_DB_CONTAINER` | 아니오 | 허용 목록 등록·정리·초대 만료 시나리오에 쓰는 로컬 DB 컨테이너 이름 |
| `AUTH_TEST_EMAIL_PREFIX` | 아니오 | 합성 계정 접두사. 기본값 `auth-e2e` |

설정이 비어 있으면 `playwright.auth.config.ts`가 **바로 중단**한다. 설정 없는 서버로 띄우면
앱이 "설정 필요" 화면을 그려 모든 단언이 엉뚱하게 실패하기 때문이다.

> **관리자 키는 앱의 `.env.local`에 넣지 않는다.** 그 파일은 앱 서버가 읽으므로 앱 프로세스가
> 값을 상속한다. 위 값들은 **테스트 명령의 환경으로만** 넘긴다.
> 인증 E2E 설정은 앱 서버로 넘기는 환경에서 `*SERVICE_ROLE*` 키를 빈 값으로 덮어써
> 상속을 막는다(`tests/auth/web-server-env.ts`, 단위 테스트로 고정). 러너와 픽스처는 그대로 읽는다.

`AUTH_TEST_DB_CONTAINER`가 없으면:

- 공간 생성 허용 목록 등록은 **실행되지 않고** 필요한 SQL만 출력된다(직접 실행해야 한다).
- 초대 만료 시나리오는 건너뛴다(skip).
- 정리에서 공간을 지우지 못해 계정 삭제가 실패할 수 있다.

`AUTH_TEST_SERVICE_ROLE_KEY`가 없으면 비밀번호 재설정 시나리오를 건너뛴다(skip).

## 3. 실행 순서

```sh
# 1) 합성 계정 A~D 준비 + A를 공간 생성 허용 목록에 등록
node tests/auth/fixtures/cli.mjs setup

# 2) 인증 E2E 실행 (포트 3002, 데모 모드 강제 해제)
pnpm run test:e2e:auth

# 3) 정리: 합성 공간·요청 기록 삭제 → 계정 삭제 → 저장 파일 삭제
node tests/auth/fixtures/cli.mjs teardown

# 상태만 확인
node tests/auth/fixtures/cli.mjs status
```

재설정 스펙만 다시 볼 때는 상태를 건드리지 않고 이렇게 돌린다(계정 D만 쓴다).

```sh
pnpm run test:e2e:auth -- recovery.spec.ts
```

**초대·정원 시나리오를 포함한 전체 스위트를 다시 돌릴 때는 `teardown` → `setup`을 먼저 실행한다.**
초대·정원·만료 시나리오는 "A의 공간에 아직 B가 없는" 상태를 전제로 한다.
또 비밀번호 재설정 스펙은 계정 D의 비밀번호를 실행 중에 바꾸므로, 저장 파일의 D 비밀번호는
그 실행 이후 더 이상 맞지 않는다(D는 그 스펙에서만 쓴다).

## 4. 계정 역할

| 계정 | 역할 |
| --- | --- |
| A (`auth-e2e-a@test.invalid`) | 공간 생성 허용 계정. 공간을 만들고 초대를 보낸다 |
| B (`auth-e2e-b@test.invalid`) | 초대 대상. 수락 후 두 번째 구성원이 된다 |
| C (`auth-e2e-c@test.invalid`) | 외부 계정. 공간 생성 권한이 없고 초대 대상도 아니다. 세션 폐기 시나리오에도 쓴다 |
| D (`auth-e2e-d@test.invalid`) | 비밀번호 재설정 전용. 이 계정의 비밀번호만 실행 중에 바뀐다 |

## 5. 스펙이 확인하는 것 (총 14개, 파일 이름 순으로 실행)

### `e2e/invite.spec.ts`

- 같은 주소로 초대 다시 만들기(화면을 다시 불러오지 않고), 폐기 후 다시 만들기
- 만료된 초대 → "만료" 안내, 공간에 들어가지 못함 (DB 컨테이너가 있을 때만)
- 대상이 아닌 계정(C) → 사용할 수 없는 초대 링크, 공간도 생기지 않음
- 대상 계정(B) 수락 → 주소에서 fragment 즉시 제거, 두 사람 공간, 탭 보관 값 삭제,
  같은 사용자의 재수락은 멱등 성공, **다른 계정의 재사용은 거부**
- 정원이 차면 새 초대를 만들 수 없음
- 토큰 없이 `/invite`에 들어오면 새 초대를 요청하라고 안내
- 설정: 본인 닉네임만 바뀌고 상대방 닉네임은 그대로

### `e2e/recovery.spec.ts`

- 재설정 메일 요청은 계정 존재 여부를 알려 주지 않음
- 관리자 API로 만든 `token_hash` → `/auth/confirm` → 새 비밀번호 저장 →
  **그 비밀번호로 실제 로그인** → 같은 토큰 재사용은 거부
  (콜백이 **같은 출처**로 돌아오는지도 함께 단언한다. 출처가 바뀌면 세션 쿠키가 전달되지 않는다)
- 잘못된 `token_hash`·허용하지 않는 `type`·토큰 없음 → 안내와 함께 거부
- PKCE 콜백 실패·공급자 오류·코드 없음 → 내부 화면으로만 이동
- 콜백의 `next`로 외부 주소에 나갈 수 없음

> 한계: **실제 메일 발송·수신은 검증하지 않는다.** 로컬 Auth의 `SITE_URL`/`URI_ALLOW_LIST`가
> 3000을 가리키고 앱은 3002라, 메일 링크가 앱으로 돌아오는 경로는 확인되지 않았다.
> 이 스펙은 "token_hash를 받은 앱 경로"만 확인한다. Auth 설정·컨테이너는 바꾸지 않았다.

### `e2e/refresh.spec.ts`

- 저장된 세션의 만료 시각을 과거로 바꾼 뒤 보호된 화면에 들어가면
  → 응답에 **갱신된 세션 쿠키가 실리고**(Set-Cookie), 응답은 `no-store`이며,
  저장된 access token이 **실제로 새 값으로 바뀌고**, 화면이 정상 동작한다.
- 서버에서 refresh token을 폐기한 뒤 같은 상황을 만들면 → 갱신 실패 → 로그인 화면으로 이동.

> **무엇이 모의이고 무엇이 진짜인가**: 바꾸는 것은 브라우저에 저장된 세션의 `expires_at`뿐이다
> (= 클라이언트가 가진 만료 정보). refresh token은 로컬 Auth가 발급한 **유효한 값 그대로**이며,
> 갱신 호출·새 토큰 발급·쿠키 재작성은 실제로 일어난다.
> 서버 벽시계로 실제 만료되는 상황(JWT_EXP 단축)은 검증하지 않았다.

### `e2e/session.spec.ts`

- 비로그인 상태로 `/`, `/settings`, `/memories`에 직접 들어가면 로그인 화면으로 이동
- 개인 화면 응답에 `Cache-Control: no-store`
- A 로그인 → 공간 생성 → 홈 표시
- 실제 모드의 `/memories`는 데모가 아니라 실제 추억 목록(MEM-001, 데모 문구가 전혀 없음)
- `?next=https://evil.example`로 외부 주소에 나갈 수 없음
- 세션이 새로 고침·같은 컨텍스트의 새 탭에서 유지되고, 로그아웃하면 **세션 쿠키가 남지 않으며**
  보호된 주소가 열리지 않음
- **두 탭**: 한 탭에서 로그아웃하면 다른 탭도 로그인 화면으로 바뀌고 그 탭에 보관된 초대 토큰이 사라짐
- 허용 목록에 없는 계정(C)은 공간을 만들 수 없고 권한 오류를 그대로 봄
- 잘못된 비밀번호는 계정 존재 여부를 알려 주지 않음

## 6. 화면 판정 규칙 (중요)

Next.js의 서버 리다이렉트는 **스트리밍으로 전달**된다. 보호된 경로를 비로그인으로 요청하면
`Location` 헤더 없이 HTTP 200이 오고, 이동은 그 뒤에 클라이언트에서 일어난다.

그래서 이 스위트는 `page.goto()` 직후의 주소를 믿지 않는다. `waitForScreen(page, [...])`으로
**실제로 그려진 화면**을 기다린 뒤 경로를 확인한다. 1차 실행에서 두 테스트가 실패하고 10개가
실행되지 못한 원인이 바로 이 가정이었다(주소가 아직 `/`인 중간 상태에서 단언이 통과해 버렸다).

## 7. 확인하지 않는 것

- 실제 SMTP 발송·수신과 메일 템플릿(로컬 메일 서비스 포함)
- 서버 벽시계 기준 토큰 만료(JWT_EXP 단축)
- 모바일 뷰포트·실기기, 접근성 자동 검사
- 배포 환경, 운영 계정·운영 데이터
