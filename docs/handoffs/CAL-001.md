## 구현 범위

각자의 개인 일정과 공동 데이트 일정을 한 달력에서 보는 `/calendar`를 실제 인증 공간에 연결했다.
조회는 사용자 세션 + RLS로 하고, 변경은 전용 RPC로만 한다. 다른 공간·비로그인은 존재 여부도 알 수 없다.

- 보기: **월 보기**(일요일 시작 격자)와 **목록 보기**(날짜별 묶음). 달 이동, "이번 달"로 복귀.
- 종류: `personal`(owner 있음) / `date`(owner null). 상태: `scheduled | done | cancelled`.
- 필드: 제목(1~100자), 장소(≤100자), 메모(≤2,000자), 종일 여부, 시작·종료 날짜/시각, 상태, 위시 연결.
- 권한: 두 사람 모두 **모든 일정을 조회**한다. 개인 일정은 **소유자만** 수정·삭제·완료 체크하고,
  공동 일정은 두 사람 모두 한다.
- 필터: 범위(`내 일정`·`상대 일정`·`함께`)와 상태. 달·보기·필터 모두 URL에 남아 뒤로 가기에도 유지된다.
- 위시 연결: 선택 사항이며 **같은 공간의 위시만** 허용한다(복합 FK `(wish_item_id, space_id)`).
- 변경은 `expectedVersion`(충돌)과 `requestId`(중복 요청)를 함께 쓴다.

### 시각을 다루는 방식 (이 작업의 핵심 설계)

클라이언트가 `timestamptz`를 만들지 않는다. 화면은 **날짜(`YYYY-MM-DD`)와 시:분(`HH:MM`)을 따로** 보내고
DB가 한국 시간(Asia/Seoul)으로 조립한다. 브라우저 시간대가 달라도 두 사람이 같은 날짜를 본다(DESIGN 1).

- 종일 일정: 시작·종료가 KST 자정에 정렬되고 **종료일이 포함**된다(하루 일정은 시작=종료).
- 시간 일정: 종료는 선택이며 시작보다 뒤여야 한다. 자정을 넘기는 일정은 정상이다.
- 표시도 KST로 계산한다(`src/features/calendar/datetime.ts`). 오프셋 상수를 화면 코드에 흩뿌리지 않는다.

### 마이그레이션을 새 파일로 추가한 이유

`20260923140100_calendar_events_cal001.sql`은 이미 검토를 받고 로컬 테스트 DB에 적용된 파일이다.
저장소 관례(DB-001·FOOD-001·WISH-001)대로 **적용된 마이그레이션은 고치지 않고 전진 마이그레이션을 더한다.**
새 파일은 `save_calendar_event`를 같은 시그니처로 `create or replace`하므로 EXECUTE 권한이 유지되고,
파일 끝의 자체 점검이 권한·`search_path`·"위시 제약 이름을 확인하는지"를 강제한다.
검토가 인용한 원본 파일의 줄 번호도 그대로 남아 재검토 diff가 좁아진다.

### 고치기 전 실패를 확인한 것 (negative proof)

"테스트가 결함을 실제로 잡는지"를 확인한 항목이다. 확인 뒤 모든 임시 되돌림을 복원했고,
최종 트리에는 되돌림·백업 파일이 남아 있지 않다(`git status`와 파일 검색으로 확인).

| 항목 | 고치기 전 결과 |
| --- | --- |
| P3-4 SQL 단언 | 옛 함수(모든 FK 위반을 위시로 매핑)를 다시 적용하고 실행 → `TEST FAIL … 실제 GF409 / 기대 23503`으로 실패 |
| P3-1 E2E | 옛 분기(성공 시 주입 없음)로 되돌리고 실행 → `expect(locator).toHaveValue` 실패 |
| P3-2 E2E | 옛 `groupByDate` + 무조건 렌더로 되돌리고 실행 → 앞뒤 달 칸에서 `toHaveCount(0)` 기대에 1이 나와 실패 |

재렌더 결과를 같은 응답으로 돌려주므로 자기모순 창이 한 커밋 경계만큼 짧고, Playwright의 자동 재시도
단언이 이미 고쳐진 화면을 본다. 그래서
  * 제품 수정은 유지했다(서버 왕복 타이밍에 의존하지 않게 만드는 것이 목적이다),

  * 버튼 목록 규칙은 `nextStatusChoices` **단위 테스트로 결정적으로** 고정했다.
이 사실을 스펙 파일 주석과 이 보고서에 그대로 적어 둔다. 제품 코드에 테스트용 지연 고리는 넣지 않았다.

## DB 계약 추가 (CONTRACTS.md 미반영)

새 테이블 `public.calendar_events`와 RPC 3개를 추가하고, 기존 `delete_wish`의 **본문만** 교체했다.
`docs/database/CONTRACTS.md`는 총괄 소유 공유 문서라 수정하지 않았다. **통합 시 아래 내용을 반영해야 한다.**

`calendar_events`는 `authenticated`·`service_role`에 **SELECT만** 부여했다. 쓰기 정책은 만들지 않아
직접 INSERT/UPDATE/DELETE는 권한과 정책 양쪽에서 막힌다.

### `save_calendar_event(p_event_id uuid, p_kind text, p_title text, p_location text, p_note text, p_all_day boolean, p_start_date date, p_start_time time, p_end_date date, p_end_time time, p_wish_item_id uuid, p_expected_version integer, p_request_id uuid) → jsonb`

상태는 다루지 않는다. 새로 만들면 항상 `scheduled`다(`save_restaurant`·`save_wish`와 같은 분리).

- 생성: `p_event_id = null`, `p_expected_version = 0`. 수정: 행을 잠그고 버전 확인 후 `version + 1`.
- **시각은 서버가 조립한다.** 날짜+시각을 Asia/Seoul 벽시계로 받아 `timestamptz`로 만든다.
  - `p_all_day = true`: `p_start_time`·`p_end_time`은 반드시 `null`. `p_end_date`는 선택(비우면 시작일).
    종료일이 시작일보다 앞이면 `GF422`. 저장 결과는 KST 자정 정렬 + 포함 종료일이다.
  - `p_all_day = false`: `p_start_time` 필수. 종료는 선택이며 **`p_end_time`이 있어야** 저장된다
    (`p_end_date`만 보내면 `GF422`). `p_end_date`를 비우면 시작일로 본다. 종료 ≤ 시작이면 `GF422`.
- `kind`·`owner_id`는 생성 후 **바꿀 수 없다**. 수정 시 `p_kind`가 기존과 다르면 `GF422 {"kind":"immutable"}`.
- 개인 일정의 `owner_id`는 **항상 만든 사람**이다. 클라이언트가 소유자를 지정할 수 없다.
- 권한: 공동 일정은 두 구성원 모두, 개인 일정은 소유자만. 상대 개인 일정 수정은 `GF403 {"ownerId":"not_owner"}`
  (존재를 숨기지 않는다 — 조회는 허용되므로 숨길 의미가 없다).
- 위시 연결: `p_wish_item_id`가 있으면 같은 공간의 위시여야 한다. 아니면 `GF404 {"wishItemId":"missing"}`.
  위시 행을 `FOR KEY SHARE`로 잡아 삭제와 직렬화한다.
- 반환: `{"eventId","version","kind","ownerId","status","allDay","startsAt","endsAt","wishItemId"}`
- 오류: `GF401`, `GF403`(소유자 아님), `GF404`(없음/타 공간/위시 없음), `GF422`, `GF409`(버전 불일치,
  requestId 입력 불일치, `{"wishItemId":"gone"}`)

### `set_calendar_event_status(p_event_id uuid, p_status text, p_expected_version integer, p_request_id uuid) → jsonb`

- `p_status`: `scheduled | done | cancelled`. **완료 체크는 삭제와 다르다**(완료 일정은 남는다, DESIGN 5.3).
- 행을 잠그므로 같은 일정의 내용 수정·삭제와 직렬화된다. 권한 규칙은 `save_calendar_event`와 같다.
- 반환: `{"eventId","version","status"}` · 오류: `GF401`, `GF403`, `GF404`, `GF422`, `GF409`

### `delete_calendar_event(p_event_id uuid, p_expected_version integer, p_request_id uuid) → jsonb`

- 행을 잠그고 버전을 확인한다. 확인 창을 연 뒤 상대가 무엇이든 바꿨으면 아무것도 지우지 않고 `GF409`.
- 연결한 위시는 **지워지지 않는다**(일정만 사라진다).
- 반환: `{"eventId"}` · 오류: `GF401`, `GF403`, `GF404`, `GF409`

### `delete_wish(uuid, integer, uuid)` — 본문 교체 (시그니처·권한 그대로)

WISH-001 계약에 **거부 조건 한 가지가 추가**됐다. 나머지는 같다.

- 연결된 일정이 있으면 지우지 않고 `GF409 {"wishId":"has_calendar_events"}`.
- 위시 행을 `FOR UPDATE`로 잠그므로 새 일정 삽입(FK가 위시 행에 `FOR KEY SHARE`를 잡는다)과 직렬화되고,
  검사 뒤 끼어들 틈이 없다.
- 앱은 이 힌트로 "연결된 일정이 있어 지울 수 없어요"를 안내한다(위 "기존 파일 수정" 참고).

## 설계 결정 (DESIGN.md에 명시가 없어 이 작업에서 정한 것)

1. **`location`(장소) 열을 추가했다.** DESIGN 5.2의 `calendar_events` 열 목록에는 없지만 CAL-001 지시가
   장소를 요구한다. 추억의 장소와 같은 100자 상한을 쓴다. **설계 문서와의 차이이므로 총괄 확인이 필요하다.**
2. **`kind`와 `owner_id`는 불변이다.** 개인↔공동 전환은 권한 주체가 바뀌는 일이라 MVP에서는 새로 만들게 한다.
   조용한 권한 이전을 만들지 않는다. 화면도 수정 시 종류 선택을 잠근다.
3. **개인 일정의 owner는 항상 만든 사람이다.** 상대방을 소유자로 지정하는 입력을 받지 않는다.
4. **상대 개인 일정 수정은 `GF403`이다(`GF404` 아님).** 조회는 두 사람 모두 허용되므로 존재를 숨길 의미가
   없고, "왜 못 바꾸는지"를 알려 주는 편이 정확하다. 외부 공간 계정에는 그대로 `GF404`다.
5. **연결된 일정이 있는 위시는 삭제를 거부한다.** 선택지는 ① 연쇄 삭제 ② 자동 연결 해제 ③ 거부였다.
   ①②는 사용자가 모르는 사이에 계획이 사라지거나 관계가 끊긴다. ③은 무엇을 먼저 정리해야 하는지 안내할 수 있다.
6. **복합 FK는 `on delete no action`이다(`restrict` 아님).** 공간 삭제는 위시와 일정을 함께 cascade로
   지우는데, `restrict`는 즉시 검사해서 공간 정리 자체를 실패시킨다. `no action`은 문장 끝에 검사하므로
   둘이 함께 사라지는 경우를 통과시킨다. 사용자 경로는 `delete_wish`가 먼저 막고 FK는 마지막 방어선이다.
7. **종일 일정의 자정 정렬은 CHECK가 아니라 트리거로 검사한다.** `at time zone`은 IMMUTABLE이 아니어서
   CHECK 제약에 쓸 수 없다. 범위(`ends_at >= starts_at` 등)는 CHECK로, 자정 정렬은
   `tg_calendar_time_guard`로 검사한다.
8. **`calendar_events_id_space_key unique (id, space_id)`를 미리 두었다.** DATE-001의 `memory_links`가
   `(calendar_event_id, space_id)` 복합 FK로 바로 쓸 수 있다.
9. **한 달 조회에 커서 페이지네이션을 두지 않았다.** 대신 상한 500과 초과 안내를 둔다.
10. **상태 바꾸기 버튼 글자는 값마다 그대로 적는다**(`STATUS_ACTION_LABELS`). `${라벨}로 바꾸기`로
    조립하면 한국어 조사 때문에 "예정로 바꾸기"가 된다(E2E에서 실제로 잡았다, 아래 참고).

### 구현 중 E2E가 잡아 고친 결함

1. **상태 바꾸기 버튼 글자의 한국어 조사.** `${STATUS_LABELS[value]}로 바꾸기`로 조립해

2. **`ownerLabel`을 문장에 이어 붙이던 안내.** `${ownerLabel}의 개인 일정이라…`가 닉네임이 없을 때

## 미실행·환경 제약

- **P3 수정분의 독립 재검토 미실행.** 1차 `8584d94`의 APPROVED는 이 delta에 적용되지 않는다.

## 후속 DATE-001 계약

DATE-001은 완료한 일정·위시에서 사진 추억을 만들고 기존 추억과 선택적으로 연결한다. CAL-001이 준비해 둔 것은 다음과 같다.

| 항목 | 값 |
| --- | --- |
| 완료 일정 찾기 | `calendar_events`에서 `status = 'done'`. 조회는 사용자 세션 + RLS(`space_id = app.current_space_id()`) |
| 복합 FK 대상 | `calendar_events_id_space_key unique (id, space_id)`. `memory_links`가 `(calendar_event_id, space_id) → calendar_events(id, space_id)`로 같은 공간만 강제할 수 있다 |
| 미리 채울 값 | `title`, `location`, 그리고 `starts_at`을 한국 날짜로 바꾼 값. 변환은 `src/features/calendar/datetime.ts`의 `toSeoulMoment()`를 재사용한다(추억의 `memory_date`는 달력 날짜다) |
| 종일/시간 구분 | `all_day`가 true면 `starts_at`의 KST 날짜가 곧 그 일정의 날짜다. false면 시작 시각의 KST 날짜를 쓴다 |
| 조회 모델 | `CalendarEventDetail`(`src/features/calendar/types.ts`)에 `canEdit`·`ownerLabel`·`linkedWish`가 들어 있다. 권한 표시를 다시 만들 필요가 없다 |
| 삭제 의미 | **연결된 추억을 지워도 일정은 유지된다**(DESIGN 5.3). 반대로 일정을 지우면 `memory_links`의 해당 행을 어떻게 할지 DATE-001이 정해야 한다. CAL-001은 `wish_item_id`에 대해 "자식이 있으면 부모 삭제 거부"를 골랐다(`delete_wish`). 같은 방향을 고르면 `delete_calendar_event`에도 같은 사전 검사를 **DATE-001의 migration에서** 추가해야 한다 |
| 주의 | `delete_calendar_event`는 현재 자식 행이 없다는 전제 위에 있다. `memory_links`가 생기면 위 삭제 의미를 먼저 정하고, FK 위반(`23503`)이 사용자에게 어떻게 보일지 함께 정해야 한다(앱 매핑은 이미 `CONFLICT`다) |
| 위시 쪽 | `wish_items`의 삭제는 이미 "연결된 일정이 있으면 거부"다. `memory_links`가 `wish_item_id`도 참조하면 `delete_wish`에 조건이 하나 더 붙는다 |

## 통합 준비 여부

**P3 수정·전체 검증 완료. 총괄 diff 확인과 독립 재검토 대기.**

1차 `8584d94`는 독립 검토에서 APPROVED(P0/P1/P2 없음)를 받았다. 이번 2차 delta는 **아직 검토를 받지 않았다.**
통합 전에 필요한 것:

1. 총괄이 2차 커밋의 diff를 확인한다. 범위는 CAL 소유 파일뿐이다(신규 5개, 수정 16개 = 이 보고서 포함 21개).
2. **`8584d94 → <2차 SHA>` 범위로 새 읽기 전용 Claude 독립 재검토를 실행한다.**
   이 보고서는 구현 세션의 자기 평가이며 독립 검토가 아니다. 1차 APPROVED를 이 delta에 적용하지 않는다.
3. 통합 시 `docs/database/CONTRACTS.md`에 위 "DB 계약 추가" 절 반영(총괄 소유 문서).
   `delete_wish`의 계약 변경(4.1절)과 **`save_calendar_event`의 FK 위반 처리 범위**(P3-4)도 함께 적는다.
4. 마이그레이션은 **두 파일을 순서대로** 적용한다
   (`20260923140100_calendar_events_cal001.sql` → `20260924120100_calendar_fk_mapping_cal001.sql`).
5. **통합 후 반드시** 공통 내비게이션(`NAV_ITEMS`)과 `ALLOWED_REDIRECT_ROOTS`에 `/calendar` 연결,
   위시 상세의 CAL-001 안내 문구 교체(잔여 위험 1·2·3). 독립 검토도 이것을 I-1로 지적했다.
   1·2가 빠지면 사용자는 화면에 도달할 수 없다.
6. `location` 열이 DESIGN 5.2 목록과 다른 점을 확인·기록한다(설계 결정 1번, 검토 P3-10).
7. DATE-001 착수 시 위 "후속 DATE-001 계약"의 삭제 의미를 먼저 정한다.

dev·main·다른 Worktree는 변경하지 않았다. push·force push·권한 우회·사용자 전역 설정 변경은 없다.
기존 Docker 컨테이너를 reset/recreate/stop하지 않았고 다른 컨테이너도 건드리지 않았다.
`AppShell`·인증 리다이렉트·`CONTRACTS.md`·`DESIGN.md`·`TASKS.md`는 두 차례 모두 수정하지 않았다.
비밀 키·비밀번호·토큰은 저장소·보고서·출력에 넣지 않았다(로컬 검증 값은 Git 제외 `.agent-runtime/` 아래에만 있다).
