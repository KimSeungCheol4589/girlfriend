## 3. 확인된 결함과 수정

### 결함 1 — 정규식 반복 횟수 한도 (SQLSTATE 2201B)

PostgreSQL 정규식은 `{m,n}`의 반복 횟수를 **255까지만** 허용한다.
`^https://[^[:space:]]{3,500}$`가 한도를 넘어, 정규식이 컴파일되는 순간(= `map_url`이 NULL이 아닌 값을
다루는 모든 경로) 실패했다. 두 군데에 있었다.

- `restaurants_map_url_https` CHECK 제약 (`20260919120200`)
- `public.save_restaurant`의 입력 검증 (`20260919120900`)

수정: 반복 횟수를 쓰지 않고 `+`로 바꾸고, 길이 제한은 `char_length`로 분리했다.
`restaurants_map_url_length` 제약을 새로 추가했다.
`20260919130100`의 자체 점검이 함수 본문과 CHECK 제약 정의를 훑어 같은 패턴이 다시 들어오면 실패시킨다.

### 결함 2 — 지연 제약 트리거가 커밋 시점에 호출자 역할로 실행됨 (보안·정합성)

지연(`DEFERRABLE INITIALLY DEFERRED`) 제약 트리거는 `SECURITY DEFINER` RPC가 **반환된 뒤**
COMMIT 시점에 실행된다. 그때 본문은 정의자(postgres)가 아니라 호출자(authenticated) 컨텍스트다.
`app_private.tg_space_member_limit()`의 지역 변수 초기화가 `app_private.config_int()`를 부르는 순간
`permission denied for schema app_private`가 났고, `accept_invite`는 성공을 반환했는데 COMMIT이 실패했다.

영향은 가용성만이 아니다. 같은 컨텍스트에서 트리거가 `public.space_members`를 읽으므로,
권한이 통과했더라도 **RLS에 걸러진 행만 세어 정원 검사가 무력화**될 수 있었다.

수정(`20260919130100`): **public 테이블에 붙은 트리거 함수 10개를 전부
`SECURITY DEFINER` + 고정 `search_path`로** 다시 정의했다(`CREATE OR REPLACE`이므로 트리거 재생성 불필요).

- 트리거 실행 시에는 함수 EXECUTE 권한을 다시 검사하지 않는다(생성 시점에만 검사).
  따라서 `app_private` 트리거 함수는 여전히 클라이언트가 직접 호출할 수 없다. 이를 테스트로도 확인한다.
- 마이그레이션 자체 점검 (1) 모든 트리거 함수가 SECURITY DEFINER + 고정 search_path인지,
  (2) `app_private` 트리거 함수가 anon/authenticated에 노출되지 않았는지 검사한다.
- 정적 표현식(CHECK 제약, 컬럼 DEFAULT)이 참조하는 `app_private` 함수는 같은 문제가 없다.
  함수 ACL은 표현식을 저장할 때 검사하고 행마다 다시 검사하지 않는다.

**감사 결과**: 지연 제약 트리거는 두 개다 — `space_members_limit`, `memory_photos_set_guard`.
둘 다 수정 대상에 포함했고, 즉시 실행 트리거 8개도 같은 기준으로 통일했다.
`memory_photos_order_key`는 지연 UNIQUE 인덱스라 함수가 없다. FK 제약 트리거는 시스템이 처리한다.

### 결함 3 — `finalize_upload`의 신뢰 경계 (보안)

`authenticated`가 직접 호출할 수 있었고 bytes/width/height를 호출자 값 그대로 기록했다.
"Server Action이 먼저 검증한다"는 관례는 방어가 아니다. RPC를 직접 부르면 우회된다.
파일을 하나도 올리지 않고 asset을 `ready`로 만들 수 있었다.

수정(`20260919130200`):

1. 예전 서명 `finalize_upload(uuid, bigint, integer, integer, uuid)`를 **DROP**하고,
   `service_role`에만 EXECUTE를 준 새 서명으로 교체했다.
2. 행위자를 세션이 아니라 명시 인자 `p_uploader_id`로 받고 asset의 실제 업로더와 대조한다.
3. 요청에 최종 사용자 세션 컨텍스트가 실려 있으면(`auth.uid()`가 있거나 JWT role이 `service_role`이 아니면)
   권한이 잘못 부여돼 있어도 `GF403`으로 거부한다(이중 방어).
4. 서버가 실제로 확인한 MIME을 받아 `prepare_upload` 선언값과 대조한다.

**DB는 이미지 바이너리를 디코딩하지 않는다.** 실제 디코딩·픽셀 수·EXIF 제거 검증은 신뢰된 서버 워커가
해야 하며 **아직 구현되지 않았다.** 이 변경이 보장하는 것은 검증 결과를 기록할 수 있는 주체를
신뢰된 역할로 좁혔다는 것뿐이다. 워커가 생기기 전에는 ready 전환을 하지 않는 편이 안전하다.

### 추가 — Storage 정책 (1차에서 "범위 밖"으로 미뤘던 것)

`supabase/migrations`에서 버킷과 `storage.objects` 정책을 정의할 수 있으므로 1차의 범위 판단이 틀렸다.
`20260919130300`에서 구현했다.

- 비공개 버킷 `space-assets` (public=false, 크기·MIME 제한은 열이 있을 때만 설정)
- INSERT: 자기 공간·자기가 만든 **pending** asset의 **정확한 생성 경로**에만 (`app.can_upload_object`)
- SELECT: 업로더 본인의 pending/미첨부, 또는 `ready`이면서 실제 첨부된 파일 (`app.can_read_object`).
  `deleting`은 누구에게도 열지 않는다.
- UPDATE/DELETE 정책 없음 → 덮어쓰기·사용자 삭제 불가. 정리는 BYPASSRLS인 `service_role`.
- anon 정책 없음 → 전면 거부.
- 모든 조건에 `bucket_id = 'space-assets'`를 포함한다. 다른 버킷의 정책·권한은 만들거나 바꾸지 않았다.
  `storage.objects`의 RLS는 켜져 있는지 **확인만** 하고 바꾸지 않는다.
- `prepare_upload` 응답에 `bucket`을 추가했다.

## 3.5 독립 검토 지적 반영 (3차, 이번 세션)

검토 세션: 별도 읽기 전용 Claude 세션이 `517c9a5c31b2824746967f27d1ef177ad19df43a`를 검토했다.
아래는 그 지적에 대한 처리다. 모두 `20260919140100`에 담았다.

### D2 (필수) — 새로 첨부하는 파일의 업로더 검사 누락

`save_memory`의 첨부 루프와 `save_customization`이 파일의 공간·목적·상태만 확인하고
**업로더를 보지 않았다.** RLS가 숨기던 상대의 대기·미첨부 파일이라도, UUID를 알아낸 구성원이
자기 기록이나 커버에 붙이면 그 순간 첨부되어 공개된다.

수정: **새로 붙는 파일에만** 업로더 일치를 요구한다. 호출 전에 이미 그 기록에 붙어 있던 사진
(유지·재정렬)과 바뀌지 않는 기존 커버는 두 구성원 모두 다룰 수 있다.
업로더 검사를 목적·상태 검사보다 **먼저** 하고 실패를 `NOT_FOUND`로 통일해
"그 파일이 존재하는가", "대기 중인가"를 알리지 않는다.

회귀 테스트(`50_mutations.sql`): B가 A의 ready 미첨부 파일과 pending 파일을 붙이려 하면 `GF404`,
A의 파일을 새 커버로 지정하면 `GF404`. 거부 뒤 A의 파일 상태·연결이 그대로인지도 확인한다.
유지·재정렬(B가 기존 사진 순서 변경)과 기존 커버 유지 저장은 계속 허용되는지도 함께 본다.

### D3 — 동시 실행에서 원시 `23505`가 새어 나감

공간 행 잠금은 **같은 공간**의 경쟁만 직렬화한다. 다음은 잠금이 겹치지 않아 UNIQUE가 최종 방어가 된다.

| 경우 | 최종 방어 | 이제 반환하는 코드 |
| --- | --- | --- |
| 같은 사용자가 서로 다른 공간의 초대를 동시 수락 | `space_members.user_id` UNIQUE | `GF409` |
| 같은 사용자의 첫 프로필 동시 생성 | `profiles` PK | `GF409` |
| 사전 검사 직후 다른 세션이 같은 사진을 붙임 | `memory_photos.asset_id` UNIQUE | `GF409` |

해당 INSERT만 `unique_violation` 핸들러로 감쌌다. **새 잠금을 추가하지 않았으므로
잠금 순서 문제나 교착이 생기지 않는다.** 직렬화 대신 매핑을 택한 이유다.

회귀 테스트: 동시성 시나리오 2개를 추가했다(`crossspace`, `profile`).
검증기는 원시 `23505`를 **명시적으로 실패로 판정**한다.

### D6 — `app.is_asset_attached`가 외부 계정에 첨부 여부를 알려줌

anon/authenticated에 EXECUTE가 있는데 공간 조건이 없어, 임의 UUID의 첨부 여부를 알 수 있었다.
호출자의 현재 공간으로 한정했다. 이를 호출하는 정책·헬퍼가 이미 같은 공간 조건을 함께 요구하므로
정책 의미는 달라지지 않는다. `30_rls_visibility.sql`에 외부 계정·비로그인의 known-ID 조회가 항상
`false`인지, 같은 공간 구성원에게는 정확한 값이 나오는지 추가했다.

### D7 — 기본 권한은 적용 역할에만 적용됨

`20260919120100`의 `ALTER DEFAULT PRIVILEGES`는 그 문을 실행한 역할에만 유효하다.
`20260919140100` 첫머리에 "기존 객체 소유자(`public.assets`) == 현재 역할" 가드를 넣어
역할이 섞이면 멈춘다. `postgres`가 아니면 경고도 남긴다.
문서에 필요한 적용 역할을 명시하고, 앞으로의 마이그레이션에도 같은 가드를 넣도록 적었다.
기본 권한 변경 범위(`public`·`app`·`app_private` 세 스키마, `postgres` 역할)와
그 DB 전역 영향도 함께 적었다. 다른 역할의 기본 권한은 바꾸지 않는다.

### D4/D5 재확인

지연 트리거의 실제 커밋 경로는 동시성 러너가, 로그인 역할 컨텍스트는 `60_deferred_triggers.sql`의
`SET CONSTRAINTS ALL IMMEDIATE`가 담당한다(7/7 통과에 포함). 겹침 장치는 `pg_locks`의
**자기 백엔드를 제외한** 미허용 잠금을 기다리도록 조였다.

### 표현 수정 — 서비스 키 관련 문구

이전 SECURITY 문서의 "서비스 키가 새더라도 RPC 밖에서 데이터를 바꿀 수 없다"는 오해를 준다.
`service_role`은 `BYPASSRLS`로 모든 행을 읽고, 신뢰된 RPC(`finalize_upload`)와 운영 함수
(부트스트랩 허용 목록 관리, 파일 정리)를 실행할 수 있다. 문구를 "최소 권한으로 사고 범위를 줄일 뿐,
키 유출은 전체 데이터 유출이며 부분 변경도 가능하다"로 정확히 고쳤다.

## 3.6 동시성 러너의 Git Bash 경로 문제

증상: MSYS가 `-f /tmp/db-001-concurrency/00_setup.sql` 인자를 Windows 경로로 변환해
컨테이너 안 Linux psql에 넘겼다. setup 이전에 실패했다.

수정:

- 컨테이너 안 경로를 인자로 주는 모든 docker 호출을 `dockerx()`로 감싸
  `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`를 적용한다.
- `docker cp`의 **원본만** `cygpath -w`로 호스트(Windows) 절대경로로 바꾸고, 대상은 컨테이너 경로 그대로 둔다.
  `cygpath`가 없는 환경(Linux/macOS)에서는 원본 경로를 그대로 쓴다.
- 복사 대상은 이 실행 전용 경로 `/tmp/db-001-concurrency-<pid>`다. 미리 존재하지 않으므로
  고정 경로에 대한 `rm -rf`가 필요 없다. 끝에 **이 실행이 만든 그 디렉터리만** 지운다.
- `cleanup` 트랩이 첫 줄에서 `$?`를 받아 **앞 단계의 실패를 보존**한다.
  teardown이 성공해도 `FAILED=0`으로 덮이지 않는다. teardown은 복사가 끝난 경우에만 실행한다.
- 실행 전 `docker inspect`로 컨테이너 존재를 먼저 확인한다.
