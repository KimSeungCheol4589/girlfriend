# DB-001 담당 보고서

- 작업: DB 스키마·권한·RLS·초대·수정 버전·중복 요청 기반과 DB 테스트, 통합용 계약 문서
- 브랜치: `feat/db-foundation`
- 상태: **구현 완료(코드 작성), 실행 검증·독립 검토 대기**
- 통합 준비: **아니오.** 마이그레이션 적용과 테스트 실행이 끝나기 전에는 dev 통합 대상이 아니다.

이 보고서는 이전의 "blocked — Claude 연결 실패, 제품 구현 미실행" 상태를 대체한다.
2026-09-19 사용자 승인으로 로컬 Claude 구현 세션이 실행됐고 담당 범위의 SQL·테스트·문서를 작성했다.

## 1. 실행한 것과 실행하지 않은 것

**작성함**: `supabase/migrations/**` 11개, `supabase/tests/**` 16개, `docs/database/**` 3개, 이 보고서.

**실행하지 않음**: 이 세션에는 Docker 쓰기 권한이 없었다.
마이그레이션 적용, psql 실행, 테스트 수행, 동시성 러너 실행을 **하지 않았다.**
따라서 아래 SQL은 문법·동작이 실제 DB에서 확인되지 않은 상태다. 어떤 항목도 "검증 통과"로 기록하지 않는다.

이 세션이 실제로 확인한 것은 다음 한 가지뿐이다.

- `docker ps --filter name=girlfriend-db-env-d82f` → 6개 컨테이너 running/healthy (읽기 전용 조회).

기획·설계·작업 문서(AGENTS, CLAUDE, PROJECT_PLAN, TECH_STACK, DESIGN, TASKS, docs/CLAUDE_WORKFLOW)와
작업 위치·브랜치(`feat/db-foundation`, 깨끗한 작업 트리)를 먼저 확인했다.
컨테이너를 시작·중지·재생성하지 않았고 pre-loopback 백업 컨테이너도 건드리지 않았다.
운영 DB·자격 증명·전역 설정·앱 설정 파일·중앙 TASKS.md는 변경하지 않았다.

## 3. 구현 요약

- **권한 두 겹**: 클라이언트 역할에는 9개 테이블 SELECT만 준다. INSERT/UPDATE/DELETE 권한이 없고 쓰기 정책도 만들지 않았다.
  변경은 전부 `SECURITY DEFINER` + 고정 `search_path` RPC로만 한다. `service_role`의 직접 쓰기도 회수했다.
- **비재귀 RLS**: 소속 판정을 `app.current_space_id()` 등 SECURITY DEFINER 헬퍼로 분리해 `space_members` 자기 참조 재귀를 없앴다.
  이 때문에 `FORCE ROW LEVEL SECURITY`는 쓰지 않는다.
- **부트스트랩**: `app_private.bootstrap_creators`에 운영자가 등록한 **확인된** 이메일만 공간을 만들 수 있다.
  목록이 비면 전면 거부. 클라이언트는 허용 여부를 입력으로 주장할 수 없다.
- **초대**: DB가 토큰을 만들고 SHA-256 해시만 저장한다. 원문은 생성 응답에 한 번만 나가고 멱등성 결과에도 남기지 않는다.
  24시간 만료, 새 초대 생성 시 이전 활성 초대 폐기, 대상 이메일 일치, 공간 행 `FOR UPDATE`로 동시 수락 직렬화,
  정원 2명, 같은 사용자 재시도는 성공 반환, 다른 사용자 재사용은 `INVITE_INVALID`.
  `space_invites`에는 어떤 역할에도 SELECT 권한이 없고 상태는 마스킹된 이메일로만 조회한다.
- **버전·멱등성**: 모든 수정은 행 잠금 + `expectedVersion` 비교 + 버전 `+1`. 트리거가 임의 버전 값을 거부한다.
  `mutation_requests`는 PK 삽입 → 충돌 시 `FOR UPDATE` 직렬화 → 결과 재생. 같은 키·다른 입력은 `CONFLICT`.
- **파일**: 경로는 `space_id/asset_id.ext` 생성 열이라 클라이언트가 정할 수 없다.
  pending/미첨부/deleting 파일은 업로더에게만 보이고, 상대에게는 ready이면서 실제 첨부된 파일만 보인다.
  분리된 파일은 `deleting`으로 바뀌고 응답의 `detachedAssets`로 Storage 정리에 넘어간다.
- **스키마 무결성**: 복합 FK `(id, space_id)`로 공간 간 사진·커버 링크를 차단하고,
  후기 작성자는 `space_members(user_id, space_id)` FK로 구성원임을 강제한다.
  사진 순서는 커밋 시점 검사(0부터 연속, 최대 10장), 태그 5개·각 20자·중복 불가, 섹션 JSON은 3개 키 정확히 한 번씩,
  날짜는 한국 달력 기준 미래 거부, 맛집 상태와 방문일은 항상 함께 움직인다.

DESIGN과 달라진 점 10가지는 `docs/database/SECURITY.md` 6절에 이유와 함께 정리했다.
주요 항목: `FORBIDDEN` 오류 코드 추가, 모든 변경 함수에서 `requestId` 필수,
초대 토큰 재생 안 함, `revoke_invite`/`discard_upload`/`list_space_invites` 추가,
`auth.users`에 트리거를 달지 않고 프로필을 지연 생성.

## 4. 총괄이 실행할 검증 (순서대로)

전제: 컨테이너 `supabase_db_girlfriend-db-env-d82f` 실행 중. 컨테이너를 시작·중지·재생성하지 않는다.

```sh
C=supabase_db_girlfriend-db-env-d82f

# 0) 적용 전 상태 (BASE TABLE 0개여야 한다)
docker exec -i "$C" psql -U postgres -d postgres -Atc \
  "select count(*) from information_schema.tables where table_schema='public' and table_type='BASE TABLE';"

# 1) 마이그레이션 적용 (순서 고정, 하나라도 실패하면 중단)
docker cp supabase/migrations "$C":/tmp/db-001-migrations
for f in 20260919120100_foundation.sql 20260919120200_core_tables.sql \
         20260919120300_triggers.sql 20260919120400_context_helpers.sql \
         20260919120500_privileges_rls.sql 20260919120600_rpc_space_invites.sql \
         20260919120700_rpc_assets.sql 20260919120800_rpc_memories.sql \
         20260919120900_rpc_restaurants.sql 20260919121000_rpc_settings_profile.sql \
         20260919121100_rpc_grants.sql; do
  echo "== $f"
  docker exec -i "$C" psql -U postgres -d postgres -X -q -v ON_ERROR_STOP=1 \
    -f "/tmp/db-001-migrations/$f" || { echo "FAILED: $f"; break; }
done

# 2) 단일 세션 테스트 (각 파일은 ROLLBACK으로 끝난다)
docker cp supabase/tests "$C":/tmp/db-001-tests
for f in 10_schema_constraints.sql 20_privileges.sql 30_rls_visibility.sql \
         40_space_and_invites.sql 50_mutations.sql; do
  echo "== $f"
  docker exec -i "$C" psql -U postgres -d postgres -X -q -v ON_ERROR_STOP=1 \
    -f "/tmp/db-001-tests/$f" || { echo "FAILED: $f"; break; }
done

# 3) 동시성 테스트 (두 세션 겹침. 픽스처는 러너가 정리한다)
sh supabase/tests/concurrency/run_race_tests.sh
```

판정: 모든 단계의 종료 코드가 0이고 출력에 `TEST FAIL`·`동시성 실패`가 없어야 한다.
11번 마이그레이션 끝의 자체 점검이 권한·RLS·search_path 위반을 그 자리에서 실패시킨다.

실패 시에는 **오류 메시지와 파일·줄 번호를 그대로 남기고** 같은 브랜치의 구현 호출에서 수정한다.
부분 성공을 통과로 기록하지 않는다.

## 5. 독립 검토

- 이 세션의 자기 점검은 독립 검토가 아니다.
- 총괄이 구현 커밋 SHA를 고정한 뒤, 파일 편집 도구 없이 읽기 전용 도구만 준 **새 Claude 세션**으로 검토한다.
- 검토 대상: `supabase/migrations/**`, `supabase/tests/**`, `docs/database/**`.
- 검토 대상 SHA: 커밋 후 총괄이 이 문서에 기록한다(현재 미커밋).

검토 시 특히 볼 것으로 제안하는 지점:

1. RLS 정책이 실제로 비재귀인지, 소유자 우회 전제(FORCE 미사용)가 깨지지 않는지.
2. `accept_invite`의 잠금 순서(공간 → 초대)와 조기 반환 경로에 정원 우회가 없는지.
3. `begin_request` 루프가 교착이나 무한 반복에 빠질 조건이 있는지.
4. `save_memory`의 사진 집합 교체 순서(연결 해제 → deleting 표시 → 재연결)에 파일 유실·재사용 구멍이 없는지.
5. 응답·오류 DETAIL에 토큰·이메일·본문이 새는 경로가 없는지.

## 6. 미실행 검증과 잔여 문제

미실행(이 세션 기준):

- 마이그레이션 적용, SQL 문법 확인, 테스트 5종 실행, 동시성 러너 실행.
- PostgREST 경유 호출(스키마 캐시, 오류 코드 전달 형태) 확인.
- 실제 Storage 업로드·다운로드 연동.

잔여 문제·후속 작업:

1. **Storage 정책 미포함.** `storage.objects` RLS와 버킷 생성은 이 범위에 넣지 않았다.
   `assets` 테이블을 기준으로 후속 작업에서 만들어야 한다. 그 전에는 파일 본문 접근이 DB 정책으로 보호되지 않는다.
2. **`finalize_upload`의 bytes/width/height는 호출자 신뢰값**이다. Server Action이 Storage에서 실제 파일을
   검증한 뒤 호출해야 한다. 더 강하게 막으려면 `service_role` 전용 변형이 필요하다.
3. **파일 정리 스케줄 없음.** `app_private.expire_stale_assets()` 주기 실행은 배포 환경 설정 사항이다.
4. **`mutation_requests` 보존 정책 없음.** 운영 전에 보관 기간과 정리 작업을 정해야 한다.
5. **down 마이그레이션 없음.** 되돌리기는 README의 DROP 절차를 로컬에서만 쓴다.
6. **`auth.users`의 `deleted_at`/`banned_until`을 보지 않는다.** GoTrue 스키마 차이로 인한 적용 실패를 피하려는
   선택이며, 정지 계정 차단은 Auth 계층 몫이다.
7. **공간 탈퇴·구성원 교체·공간 삭제 없음**(DESIGN 1절대로 MVP 제외). `assets` 참조가 RESTRICT라 수동 절차가 필요하다.
8. 테스트가 `auth.users`에 합성 계정을 직접 넣는다. GoTrue 스키마가 바뀌면 `tests_support.make_user`의 열 목록을 맞춰야 한다.
