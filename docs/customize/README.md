# 꾸미기(THEME-001) 구현 메모

실제 인증 공간의 `/customize`에서 테마·포인트 색상·커버·홈 섹션을 **두 사람이 함께 쓰는 설정**으로
저장한다. 기준은 DESIGN.md 4.1·4.2·8.2·8.3과 docs/database/CONTRACTS.md 2·5다.

데모 화면(`src/features/customization/**`)은 그대로 둔다. 실제 제품은 `src/features/customize/**`에
따로 있고, 두 경로는 서로를 부르지 않는다(데모 저장소와 실제 저장을 섞지 않기 위해).

## 무엇을 어디에 저장하는가

| 값 | 저장 위치 | 저장 방법 |
| --- | --- | --- |
| 테마·포인트 색상·커버·홈 섹션 | `space_settings` 한 행 | `save_customization` 한 번 |
| 추억 고정 여부 | `memories.is_pinned` | 기존 `setMemoryPinnedAction`(save_memory)로 **한 건씩** |

**고정은 꾸미기 저장에 들어가지 않는다.** 설정 스냅샷에는 고정한 기록 ID가 없다. 화면도 두 저장을
분리해 각각의 성공·실패를 보여 준다. "함께 저장됐다"고 말하지 않는다.

## 저장 규칙

- `expectedVersion`은 화면이 읽은 설정 버전이다. 상대가 먼저 저장했으면 DB가 `CONFLICT`로 거부한다.
  이때 화면은 **고른 값을 그대로 두고**, 최신 설정을 불러올지 사용자가 직접 고르게 한다.
  자동으로 덮어쓰거나 자동으로 초안을 버리지 않는다.
- `requestId`는 같은 내용을 다시 보낼 때 유지하고, 내용을 고치면 새로 만든다(CONTRACTS.md 7-1).
  응답을 잃은 재전송이 두 번 반영되지 않는다.
- 미리보기는 미리보기 영역에만 CSS 변수와 `data-theme`를 씌운다. 문서 전체 테마(`ThemeScope`)와
  공유 설정은 ‘저장’ 후에만 바뀐다.
- 취소는 마지막으로 저장한 값으로 되돌린다. 저장하지 않은 고정 초안도 함께 되돌리지만,
  **이미 저장한 고정은 되돌리지 않는다.**

## 커버 사진

추억 사진과 **같은 버킷·같은 제한·같은 파이프라인**을 쓰고 용도(`purpose`)만 `cover`다.

1. 브라우저가 정규화한다(방향 반영·긴 변 2,048px·WebP/JPEG 재인코딩·EXIF 제거).
2. `prepare_upload(purpose='cover')` → 사용자 세션으로 **한 번만** 업로드(upsert 없음).
3. 서버가 객체를 읽기 전용으로 내려받아 실제 디코딩·치수·메타데이터를 검사하고
   `finalize_upload`(service 전용)를 호출한다.
4. 확정된 파일은 **‘저장’을 눌러야** `save_customization`으로 설정에 붙는다.

공용 확정기 `finalizeOwnedMemoryPhoto(deps, assetId, purpose)`의 세 번째 인자는 **필수**다.
기본값을 두면 커버 경로에서 추억 사진이 커버로(또는 그 반대로) 확정될 수 있다. 용도가 다르면
존재 여부를 알리지 않고 `NOT_FOUND`다(회귀 테스트: `tests/customize/unit/finalize-purpose.test.ts`).

### 파일 정리

- 교체·해제된 이전 커버는 DB가 `detachedAssets`로 알려 준 것만 정리한다. 브라우저가 보낸 경로는 쓰지 않는다.
- 정리에 실패해도 **설정 저장은 성공**이다(`cleanup: 'pending'`). 저장을 실패로 뒤집어 알리지 않는다.
- 아직 저장하지 않은 내 파일만 교체·해제·화면 이탈에서 `discard_upload`로 되돌린다.
  저장에 쓰인 파일은 정리 대상에서 빠지고, DB도 첨부된 asset의 취소를 거부한다.
- 저장 요청이 진행 중일 때는 결과를 모르므로 정리하지 않는다.
- **탭 닫기·새로고침·강제 종료는 정리 요청이 끝난다는 보장이 없다.** 그렇게 남은 파일은
  24시간 만료 정리 대상이다(docs/memories/CLEANUP.md와 같은 경로). 이 한계는 추억 사진과 같다.

### 무엇을 보고 커버를 그리는가

홈과 꾸미기 화면은 `space_settings.cover_asset_id` **값 자체**를 커버로 쓴다. 그 값을 붙인
`save_customization`이 이미 같은 공간·`purpose='cover'`·`state='ready'`·업로더를 검사했기 때문이다.

화면을 그리기 전에 `assets` 행을 한 번 더 읽어 거르지 않는다. 그 조회가 막히면 **실제로 저장된
커버가 조용히 사라진 것처럼** 보이기 때문이다(2026-09-23 E2E에서 홈 커버가 보이지 않은 증상의
유력한 원인). 사진을 실제로 내려받을 수 있는지는 인증 경로가 세션·Storage 정책으로 판단하고,
불러오지 못하면 홈은 테마 배경만 보여 준다.

"이 커버를 내가 올렸는지"는 안내 문구에만 쓰는 힌트다. 읽지 못하면 `null`(모름)로 두고,
모르는 것을 아는 척하지 않는다(누가 올렸는지 단정하지 않되 "새 커버는 올린 사람만 지정할 수
있다"는 사실은 그대로 알린다).

### 권한

- 새 커버는 **올린 사람만** 지정할 수 있다. 상대가 올린 미첨부 파일을 지정하면 `NOT_FOUND`다.
- 이미 붙어 있는 커버는 두 구성원 모두 유지·해제할 수 있다.
- 조회는 `/customize/cover/<assetId>` 인증 경로뿐이다. 서명 URL·공개 URL·이미지 최적화 서버를
  쓰지 않고 `private, no-store`로 응답한다. 외부 계정·비로그인·다른 용도 파일·없는 ID는 모두 404다.
- 서버에 `MEM_SUPABASE_SERVICE_ROLE_KEY`가 없으면 **새 업로드만** 막는다. 이유를 화면에 적고,
  나머지 저장과 이미 저장된 커버 조회는 그대로 둔다.

## 홈 반영

`src/app/page.tsx`가 저장된 설정을 읽어 커버와 섹션 순서·표시 여부를 넘긴다.
`LiveMemorySummary`가 `pinned` · `recentMemories` · `wishlist`를 **저장된 순서대로** 그리고,
숨긴 섹션은 빼며, 전부 숨기면 그 사실을 알린다.

맛집 섹션은 FOOD-001이 실제 기능을 만드는 중이라 예시 맛집을 만들지 않고 준비 중임을 적는다.
순서·표시 설정은 그 자리에도 지금 그대로 적용된다.

## 알려진 한계

- 브라우저 뒤로/앞으로 가기는 미저장 확인 대화상자로 막을 수 없다(App Router에 취소 API가 없다).
  앱 안의 링크 이동은 `UnsavedGuard`가, 탭 닫기·새로고침은 `beforeunload`가 맡는다.
- 충돌 뒤 "최신 설정 불러오기"는 꾸미기 설정만 다시 읽는다. 고정 후보 목록은 각 줄이 자기 스냅샷과
  버전으로 따로 저장하므로 충돌도 그 줄에서 따로 알린다.
- `space_settings` 행을 읽지 못하면 꾸미기 화면은 기본값으로 편집을 시작하지 않고 실패를 알린다.
  기본값으로 저장하면 상대가 저장해 둔 설정을 모른 채 덮어쓰기 때문이다.
